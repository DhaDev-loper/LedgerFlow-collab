# WRS Accounting System

A double-entry bookkeeping and cash flow management system for a water refilling station business.

## Tech Stack
- PHP (vanilla, no framework)
- MySQL
- Vanilla HTML/CSS/JS + Bootstrap 5
- PHPMailer (via Composer) for email delivery

## User Role Titles

User accounts retain the internal role values `owner`, `admin`, `accountant`,
and `staff` for database compatibility and authorization checks. The interface
displays them as CEO, CFO, Senior Accountant, and Accounts Executive,
respectively. These are display-title changes only; they do not change
permissions or require a role-data migration.

## Setup Instructions

### 1. Get the code
```bash
git clone <your-repo-url>
```
Place it inside your local server's web folder:
- **Laragon:** `C:\laragon\www\`
- **XAMPP:** `C:\xampp\htdocs\`

### 2. Install PHP dependencies
From inside the project folder:
```bash
composer install
```
This installs PHPMailer into a `vendor/` folder (not included in the repo — regenerated by this command).

### 3. Set up your database
1. Start MySQL (via Laragon or XAMPP)
2. Open phpMyAdmin (XAMPP) or HeidiSQL (Laragon)
3. Import `backend/database/schema.sql` once. It creates/selects the
   `wrs_accounting` database and includes the changes from the migration files.

`backend/database/schema.sql` is the complete fresh-install schema for the
application, including account codes, journal deletion approvals, receipt-scan
sessions, audit history, and settlement allocations. For a fresh installation,
do not run the migration files separately. Do not import the schema over an
existing database; use the listed migrations to update an existing installation.

If you already have an existing database, run
`backend/database/migrations/20261015_add_suspension_level.sql` once to add the
field required for progressive login suspensions, and run
`backend/database/migrations/20261015_create_audit_table.sql` once to create the
audit log table. Run `backend/database/migrations/20261015_add_single_active_session.sql`
once to enable one active login session per account. Run
`backend/database/migrations/20261015_add_cash_account_flag.sql` and
`backend/database/migrations/20261015_add_party_types_and_settlement_allocations.sql`
once to configure cash/bank account classification and customer/vendor settlement tracking.
Run `backend/database/migrations/20261015_add_account_classification.sql` once to
add current/non-current classification for Asset and Liability accounts. Set the
classification in the Chart of Accounts; the Balance Sheet groups each category
accordingly. Existing accounts default to current.
Run `backend/database/migrations/20261015_add_journal_edit_tracking.sql` once to
track journal header edits. Edited entries are highlighted and labeled in the
journal list and detail view with the latest edit timestamp.
Run `backend/database/migrations/20261015_remove_audit_ip_address.sql` once to
remove stored IP addresses from the audit table. The audit viewer now presents
actions and change details in plain language.
Run `backend/database/migrations/20261016_add_user_password_setup_invitations.sql`
once to require newly created and restored users to set their password through
a one-time invitation link.
Run `backend/database/migrations/20261016_add_client_ad_budget_liability_account.sql`
once to add the current liability account used by the client ad-budget journal
templates. The migration skips the insert if the account already exists.
Run `backend/database/migrations/20261018_add_self_service_password_recovery.sql`
once to enable secure, single-use account recovery links that expire after 15 minutes.
Run `backend/database/migrations/20261104_add_accounting_period_locks.sql` once
to enable monthly/yearly period locks and links between new adjustment entries
and their original closed-period entries.
Run `backend/database/migrations/20261107_add_client_logo.sql` once to add client
logo paths for the Clients Directory.
Run `backend/database/migrations/20261107_add_projects_and_project_journals.sql`
once to add active-by-default projects and project links on journal entries.

Successful logins and journal, account, client, and user-management changes are
recorded in `audit`. Audit details intentionally exclude credentials and
password/PIN values. The audit insert is committed with related writes where
the route uses a database transaction.
Owners and admins can open the audit viewer at `backend/audit-log.php` or use
the Audit Log button in User Management. The viewer supports search, action and
entity filters, date filters, and pagination.

The Appearance setting stores a light/dark preference in the current browser
and applies it across the application modules, including shared navigation,
forms, tables, and modals. Dark mode is the default; saved preferences can be
changed later in Settings.

An account cannot sign in on a second device while its current session is
active. A signed-in session expires for this purpose after 30 minutes without
an authenticated request; otherwise, the user must log out before signing in
on another device. Owners can take over a recent session by signing in with
their password and verifying their PIN; the previous session is invalidated
only after the PIN is correct.
The application also signs out an idle browser after 30 minutes without user
activity, with a one-minute warning beforehand.

Non-owner accounts are suspended after five failed login attempts. Successive
suspensions last 5 minutes, 15 minutes, and 60 minutes; the next cycle locks
the account by deactivating it. Users can recover access through a secure link
sent to their registered email. Recovery resets the password, failed-login
counter, and suspension level. Administrator-disabled and deleted accounts
cannot be reactivated through self-service recovery.

### Accounting period locks

Owners and admins can open **Period Locks** from User Management to close a
month or year after reports are finalized. Closing requires a reason and is
recorded in the audit log. Entries cannot be created in a closed period, and
existing entries in it cannot be edited, sent for deletion, approved for
deletion, rejected back to posted, or voided. Only the owner can reopen a
period, and reopening also requires an audited reason.

To correct a closed-period entry, create a new balanced journal entry dated in
an open period and select its original entry in **Adjustment to closed-period
entry**. The original remains unchanged and the adjustment link is shown in
the entry list and details. The selector lists the latest 500 posted entries
from closed periods. While any period is closed, new accounts must start with
a zero opening balance; record an opening balance as a new entry in an open
period so it cannot change finalized reports retroactively.

### 4. Configure environment variables
1. Copy `.env.example` to a new file named `.env`
2. Fill in your own values:
   - Database credentials (usually `root` / no password by default on both Laragon and XAMPP)
   - Gmail SMTP credentials — **you'll need your own Gmail App Password** (see below)
   - `APP_URL` — the absolute URL of the project root, used to build password setup and recovery links
   - `OCR_SPACE_API_KEY` — the server-side API key used for receipt OCR; uploaded receipt images are sent to OCR.space for text extraction

### 5. Create your Gmail App Password (for recovery/setup emails)
1. Enable 2-Step Verification on your Google Account
2. Go to https://myaccount.google.com/apppasswords
3. Generate an app password, paste it into `.env` as `MAIL_PASSWORD`

### 6. Create the first admin account
The admin seed is command-line-only and has no default email or password. Set
the initial administrator's name and email in PowerShell, then run:

```powershell
$env:ADMIN_SEED_NAME = "Initial Administrator"
$env:ADMIN_SEED_EMAIL = "your-admin@example.com"
php backend/database/seeds/seed_admin.php
Remove-Item Env:ADMIN_SEED_NAME
Remove-Item Env:ADMIN_SEED_EMAIL
```

The account cannot sign in until its one-time setup invitation is used to
choose a password. The invitation expires after 24 hours and is sent using the
configured mail settings. If email delivery fails, the seed prints the setup
link to the command line; use that link to set the password. Delete the
printed link from any terminal logs or history where practical.

### Seed the official owner account
Run `backend/database/seeds/seed_owner.php` from PowerShell after setting
`OWNER_SEED_PASSWORD` and `OWNER_SEED_PIN` in the current shell session. The
password must be at least 8 characters; the PIN must be exactly 4 digits.
These values are read at runtime and are not stored in the seed file. The
script only runs from the command line, creates `KoboSocial@gmail.com` as an
owner, and does not overwrite an existing account.

### Automated off-site backups and restore tests (Windows)

The backup scripts create a ZIP encrypted with AES-256 containing a
transaction-consistent MySQL dump, the receipt uploads, and a verification
manifest. They upload it to a private S3-compatible bucket and verify the
remote object size. Temporary local archives and dump files are removed after
the upload attempt.

1. Install the AWS CLI and the MySQL/MariaDB client tools. Ensure `php.exe` is
   on `PATH`; `mysqldump.exe` and `mysql.exe` should be on `PATH`, or in a
   Laragon `bin\mysql\<version>\bin` directory.
2. Create a private bucket with public access blocked. Configure an AWS CLI
   profile for this Windows account using the provider's recommended
   credentials; do not put access keys in `.env` or in scheduled-task
   arguments. For AWS credentials, `aws configure --profile ledgerflow-backups`
   starts the interactive profile setup; use your S3 provider's instructions
   for custom endpoints. Limit the profile to the required bucket/prefix
   operations.
3. Configure the non-secret target settings in `.env`:
   - `BACKUP_S3_BUCKET` — bucket name
   - `BACKUP_S3_PREFIX` — object prefix (defaults to `ledgerflow`)
   - `BACKUP_AWS_PROFILE` — optional AWS CLI profile name
   - `BACKUP_S3_ENDPOINT_URL` — optional endpoint for non-AWS S3-compatible
     providers
   - `BACKUP_S3_SSE` — server-side encryption setting; defaults to `AES256`
     (set blank only if the chosen provider does not support this option; the
     archive itself is still AES-256 encrypted)
4. Set `BACKUP_ARCHIVE_PASSWORD` as a Windows user environment variable for the
   account that will run the scheduled tasks. Use a unique password with at
   least 16 characters, store it securely, and retain it separately from the
   bucket credentials. Sign out and back in after setting it so scheduled
   tasks inherit it. Losing this password makes the backups unrestorable.
5. To test configuration and create the first backup manually, run
   `tools\backup-daily.ps1` from PowerShell in the repository. Check that the
   command reports an uploaded and verified `s3://` object.
6. Register daily backups and monthly restore tests for this Windows account:

   ```powershell
   .\tools\register-backup-tasks.ps1
   .\tools\restore-test.ps1
   ```

   The scheduled tasks run only while the user is logged on by default. In
   Task Scheduler, configure them to run while the user is logged off if
   needed; Windows will ask for the account password. Keep the computer on
   and ensure MySQL is available at the scheduled times.

   The test downloads the newest archive, decrypts it, restores the database
   into a randomly named temporary database, verifies its table list and
   receipt-file hashes, then drops the temporary database. It never imports
   into the live application database. The MySQL account used for the test
   needs permission to create and drop databases; set the optional
   `BACKUP_RESTORE_DB_USER` and `BACKUP_RESTORE_DB_PASS` to use a dedicated
   account instead.

Configure a bucket lifecycle rule to expire objects under the backup prefix
after your chosen retention period (30 days is a reasonable starting point).
If bucket versioning is enabled, configure expiration for noncurrent versions
as well. Test restore from an object before relying on a new provider, bucket,
or credentials. Restore tests need database space for a second copy of the
database while they run.

## Client Settlements

Client profiles show their journal history and outstanding Accounts Receivable
balance. Authorized users can record customer receipts and vendor payments from
the client profile or Transactions page; settlements are posted as balanced
journal entries using active cash/bank, Accounts Receivable, and Accounts
Payable accounts. Payments are allocated automatically to the oldest due
invoice or bill first, and cannot exceed the selected party's open balance.
Invoices and vendor bills require a customer/vendor and due date. Vendor bills
can be entered from Transactions using **Record Vendor Bill**; create or edit
parties in the Clients directory to set whether they are customers, vendors, or
both. The party migration marks existing parties with A/P activity as
customer/vendor until their records are reviewed; other existing clients keep
the customer default. Clients can be deactivated or reactivated from the
directory without deleting their profile or financial history. Inactive clients
are excluded from new transaction selectors and cannot receive new invoices or
bills, but can still be selected to settle existing A/R or A/P balances.

Cash, bank, and wallet accounts are explicitly marked in the Chart of Accounts.
The cash-flow reports and quick cash transaction selectors use this flag rather
than account-name matching. Review the migrated flags before using the updated
cash-flow summaries, and mark any newly created cash-equivalent Asset accounts
accordingly.
